# P15-C — Estorno financeiro com histórico

## Contexto

A API permite cancelar o recebimento de uma mensalidade paga, retornando seu status para pendente. O cancelamento deve virar estorno com histórico, sem apagar o fato financeiro anterior.

## Objetivo

Implementar estorno de pagamento mantendo histórico financeiro, alterando a regra existente de cancelamento de recebimento.

## Critérios BDD

Funcionalidade: Estorno financeiro com histórico

### Cenário: Administrador estorna pagamento de mensalidade paga

Dado que existe mensalidade paga por um pagamento de 200.00
Quando o administrador estorna esse pagamento
Então o estorno deve ser registrado
E a mensalidade deve voltar para pendente
E o saldo pago líquido deve ser 0.00

### Cenário: Sistema impede estorno duplicado

Dado que um pagamento já foi estornado
Quando o administrador tenta estornar o mesmo pagamento novamente
Então a API deve bloquear a operação
E não deve criar novo estorno

### Cenário: Estorno parcial recalcula saldo restante

Dado que existe mensalidade de 200.00 paga por dois pagamentos de 100.00
Quando o administrador estorna um pagamento de 100.00
Então a mensalidade deve voltar para pendente
E o saldo pago líquido deve ser 100.00

### Cenário: Consulta financeira mantém histórico de pagamento e estorno

Dado que uma mensalidade possui pagamento e estorno registrados
Quando o administrador consulta os detalhes financeiros da mensalidade
Então a resposta deve indicar o valor original, valores pagos, valores estornados e saldo líquido

### Cenário: Aluno não deve ser inativado automaticamente por estorno

Dado que um aluno ativo possui mensalidade paga
Quando o pagamento é estornado
Então a mensalidade pode voltar para pendente
Mas o aluno não deve ser inativado automaticamente, salvo se já existir regra explícita no projeto

## Regras

- O pagamento original deve permanecer preservado.
- O estorno deve ser persistido em registro financeiro próprio vinculado ao pagamento.
- Um mesmo pagamento não pode possuir estorno duplicado.
- O saldo líquido deve ser calculado como pagamentos menos estornos.
- O estorno não deve inativar automaticamente o aluno.
- Não criar frontend, dependências novas ou funcionalidades fora desta manutenção.
